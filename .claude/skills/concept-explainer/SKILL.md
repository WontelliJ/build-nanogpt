# Concept Explainer

복잡한 개념을 일반인도 따라올 수 있는 문서로 만드는 스킬이다. 독자가 용어를 외우는 대신 하나의 예시가 단계마다 어떻게 바뀌는지 따라가며 이해하게 하는 것이 목표다. 문서만 읽어도 이해되어야 하고 발표 대본은 문서를 보조한다.

## 결과물

| 파일 | 내용 |
|---|---|
| `<주제>-wiki.md` | 본문. 예시, 전체 흐름, 단계별 설명, 정리 |
| `<주제>-script.md` | 본문과 같은 순서의 발표 대본. 그대로 읽으면 되게 쓴다 |
| `<주제>-practice.md` | 본문에서 뺀 부가 정보. 코드 대응, 실습, 역사, 비교, 심화 |

사용자가 일부만 원하면 그것만 만든다.

## 작업 순서

1. 주제와 독자를 확인한다. 독자가 정해지지 않았으면 전문 지식이 없는 일반 직원을 기준으로 한다.
2. 사실을 조사하고 확인한다. 코드, 설정값, 실제 도구 출력처럼 확인할 수 있는 것은 직접 확인한다.
3. 예시를 설계한다(아래 예시 고르기).
4. 전체 흐름을 단계 목록으로 정하고 2~4개 부분으로 묶는다.
5. 본문을 쓴다(아래 문서 구조와 단계별 고정 틀).
6. 숫자 예시를 직접 계산해 맞춘다.
7. Mermaid 그림을 렌더링해 확인한다(`scripts/render_mermaid.sh`).
8. 문체를 점검한다(`scripts/check_style.sh`).
9. 대본과 부가 문서를 쓴다.
10. 아래 완성 전 점검표로 마지막 확인을 한다.

## 예시 고르기

예시가 이 문서의 뼈대다. 처음부터 끝까지 하나의 예시만 쓰고, 단계가 바뀌어도 같은 예시가 어떻게 변하는지 보여 준다.

- 헷갈릴 만한 후보를 일부러 넣는다. 정답 후보만 있으면 각 단계가 무엇을 가려내는지 보이지 않는다. 예를 들어 LLM 설명에서 '민수는 사과를 좋아해'만 쓰지 않고 '민수는 사과를 좋아하고 지수는 포도를 좋아해'를 쓰면 단계마다 지수가 아니라 민수, 포도가 아니라 사과를 고르는 과정이 드러난다.
- 예시 안에 단계마다 풀어야 할 문제가 하나씩 들어 있게 만든다. 순서가 중요한 부분, 멀리 떨어진 정보, 여러 번 건너야 이어지는 관계 등.
- 필요하면 문장이나 대화 턴을 늘린다. 추가한 요소마다 어느 단계를 설명하기 위한 것인지 분명해야 한다.

## 문서 구조

1. 예시: 구체적인 상황과 결과를 먼저 보여 주고 이 결과가 어떻게 나오는지를 문서의 질문으로 삼는다. 결과가 나오려면 무엇과 무엇이 연결되어야 하는지 표로 정리하면 좋다.
2. 전체 흐름: 단계 목록을 Mermaid 흐름도로 그리고 부분별 역할을 표로 설명한다. 큰 줄기를 먼저 잡아야 세부 설명을 읽을 때 지금 어느 부분인지 알 수 있다.
3. 단계별 설명: 모든 단계를 아래 고정 틀로 쓴다.
4. 정리: 단계, 한 일, 예시에서 달라진 것을 한 표로 모으고 전체를 한 문장으로 요약한다.
5. 부가 정보는 별도 문서로 뺀다. 본문이 길어지면 독자가 본질을 놓친다.

반복 구조가 여러 겹이면(예: 내부 반복과 바깥 반복) 처음 나오는 곳에서 표로 구분해 둔다. 한 대상이 여러 단계를 거치며 어떻게 바뀌는지 한 표로 따라가 보이면 단계가 덧씌워져 헷갈리는 것을 막을 수 있다.

## 단계별 고정 틀

모든 단계를 같은 순서로 쓴다. 독자가 틀에 익숙해지면 내용에만 집중할 수 있다. 한 단계의 남은 문제가 다음 단계의 이유가 되도록 이어 붙인다.

```markdown
## 1-2. 단계 이름

> 이 단계가 하는 일을 결론부터 한두 문장으로.

### 왜 하나
이 단계가 없으면 무엇이 안 되는지 서술형 문단으로. 예시로 보여 준다.

### 어떻게 하나
실제 방법을 순서대로. 숫자 예시, 표, Mermaid 그림을 함께 쓴다.

### 이 단계 전후
| | 전 | 후 |
|---|---|---|
| 같은 예시가 | 어땠는지 | 어떻게 달라졌는지 |

### 남은 문제
아직 해결되지 않은 것과 그것을 다음 단계가 해결한다는 연결.

<sub>용어(풀네임, 한글명): 한 줄 정의</sub>
```

실제 작성 예는 `references/example-step.md`를 본다.

## 정확성

쉬운 설명과 틀린 설명은 다르다. 단순화는 하되 틀린 말은 하지 않는다.

- 단순화한 부분은 짧게 설명용이라고 밝힌다. 문서 처음에 숫자가 설명용 값이라는 것을 한 번 밝힌다.
- 숫자 예시는 직접 계산해서 맞춘다. 비율 합, 확률 합, 곱셈과 덧셈 결과가 실제와 일치해야 한다. 독자는 숫자를 따라 계산해 보면서 이해한다.
- 앞에서 세운 규칙을 뒤의 예시가 어기지 않는지 확인한다. 예를 들어 앞쪽만 본다고 설명해 놓고 뒤에 올 단어의 정보를 이미 아는 것처럼 쓰면 안 된다. 이런 모순은 독자를 가장 크게 헷갈리게 한다.
- 예시 값이 사람이 정한 값인지, 실제 측정값인지, 학습이나 설정으로 정해지는 값인지 구분해서 적는다.
- 고정값인지 상황에 따라 바뀌는 값인지 구분해서 적는다.
- 확인하지 못한 링크나 주장은 그렇다고 밝힌다.
- 독자가 오해하기 쉬운 지점은 Q&A가 아니라 본문 설명 안에 한두 문장으로 짚는다. 예: 하나만 고르는 것이 아니라 전부를 비율대로 섞는다, 가깝다고 자동으로 더 참고하는 것은 아니다.

## 문체

해라체 평서문(~다), 두괄식, 짧은 문장으로 쓴다. 이유와 과정은 서술형 문단으로 쓰고 개조식은 나열 자체가 의미 있을 때만 쓴다. AI가 쓴 티가 나는 표현은 독자의 신뢰를 떨어뜨리므로 피한다. 쓰지 않는 표현의 전체 목록과 대안은 `references/style.md`에 있다. 핵심만 적으면:

- 굵은 글씨, 큰따옴표 강조, 긴 줄표(—), 연결어미 뒤 쉼표(바꾸고, 더한다), 명사형 종결 남발(정보 없음.), 장 번호 참조((이유는 4장)), Q&A 형식, 비유 남발을 쓰지 않는다.
- 예시 속 단어나 Token을 가리킬 때는 작은따옴표를 쓴다. 예: '사과', '그 사람'
- 비유는 꼭 필요할 때 한 줄 이내로 쓴다.

## 용어 설명

일반인이 모를 만한 용어와 약어는 처음 나오는 곳 바로 아래에 작은 글씨로 설명한다. 본문 첫머리의 핵심 용어도 빠뜨리지 않는다. 같은 용어는 두 번 설명하지 않는다.

```html
<sub>Token(토큰): 모델이 글을 처리하는 단위. 단어 하나일 수도 있고 조사 하나일 수도 있다<br>
Softmax(소프트맥스): 점수 목록을 0~1 사이, 합이 1인 비율로 바꾸는 함수</sub>
```

## 시각 자료

| 보여 줄 것 | 형식 |
|---|---|
| 전체 단계 흐름 | Mermaid flowchart TD + subgraph로 부분 묶기 |
| 한 단계의 내부 구조 | Mermaid flowchart TD |
| 관계와 비율 | Mermaid flowchart LR + 화살표 라벨에 숫자 |
| 반복 과정 | Mermaid flowchart TD |
| 전후 비교, 수치 변화, 단계 요약 | 표 |
| 계산 과정 | text 코드 블록 |

Mermaid는 라벨을 큰따옴표로 감싸고 한 줄 15자 안팎에서 `<br/>`로 줄을 바꾼다. 작성 규칙과 자주 생기는 문제는 `references/mermaid.md`에 있다. 그림은 반드시 렌더링해서 눈으로 확인한다. 문법이 맞아도 상자가 좁거나 화살표가 엉키면 읽을 수 없다.

## 발표 대본

- 본문과 같은 순서로 쓴다. 맨 위에 예상 발표 시간을 적는다.
- 화면을 바꿀 지점에 `[화면] 띄울 부분`을 적는다.
- 본문의 작은 글씨 용어 설명을 처음 나오는 자리에서 말로 풀어 넣는다. 그대로 읽으면 되게 한다.
- 표와 그림은 다 읽지 않고 핵심 숫자 한두 개만 말한다.
- 합니다체로 쓰고 한 문장에 정보 하나만 담는다.

## 완성 전 점검표

- [ ] 예시 하나로 처음부터 끝까지 이어지는가
- [ ] 큰 줄기(그림 + 표)가 단계 설명보다 먼저 나오는가
- [ ] 모든 단계가 한 줄 요약 / 왜 / 어떻게 / 전후 / 남은 문제 틀을 따르는가
- [ ] 각 단계의 남은 문제가 다음 단계의 이유로 이어지는가
- [ ] 숫자 예시를 직접 계산해 확인했는가
- [ ] 앞에서 세운 규칙을 뒤의 예시가 어기지 않는가
- [ ] 모든 전문 용어가 처음 나오는 곳에 작은 글씨로 설명되어 있는가
- [ ] `scripts/check_style.sh`가 깨끗하게 통과하는가(남은 것은 목록 나열 같은 의도한 경우뿐인가)
- [ ] `scripts/render_mermaid.sh`로 모든 그림을 렌더링해 확인했는가
- [ ] 부가 정보를 본문에서 뺐는가
- [ ] 대본이 본문과 같은 순서이고 용어 설명을 포함하는가
- [ ] 업로드할 위키가 Mermaid와 `<sub>` 태그를 지원하는지 사용자에게 알렸는가

## 피드백 반영

사용자가 질문하거나 헷갈려하면 그 지점은 다른 독자도 헷갈린다는 신호다. 질문에 답한 뒤 해당 설명을 본문에 한두 문장으로 녹여 넣는다. 질문 중에 실제 오류가 드러나면 숨기지 말고 무엇이 틀렸는지 밝히고 고친다.
