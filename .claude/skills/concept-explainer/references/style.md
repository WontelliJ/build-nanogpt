# 문체 기준

## 기본

- 본문은 해라체 평서문(~다)으로 쓴다. 대본은 합니다체로 쓴다.
- 결론부터 쓴다. 단계마다 첫 줄 인용 블록(>)이 그 단계의 결론이다.
- 문장은 짧게 쓰고 한 문장에 정보 하나를 담는다.
- 이유와 과정은 서술형 문단으로 쓴다. 개조식은 나열 자체가 의미 있을 때만 쓴다. 이유 설명을 개조식으로 쪼개면 앞뒤 연결이 끊겨 이해가 어려워진다.

## 쓰지 않는 것

| 쓰지 않는 것 | 예 | 대신 |
|---|---|---|
| 굵은 글씨 강조 | \*\*핵심\*\* | 문장 순서와 표로 강조 |
| 큰따옴표 강조 | "중요한" 단계 | 따옴표 없이 쓰기 |
| 긴 줄표 | A — B | 쉼표, 괄호, 문장 분리 |
| 연결어미 뒤 쉼표 | 바꾸고, 더한다 / 처리하며, 넘긴다 | 바꾸고 더한다. 길면 두 문장으로 나눈다 |
| 명사형 종결 남발 | 정보 없음. 해결함. | 정보가 없다. 해결한다. |
| 장 번호 참조 | (이유는 4장), (8장 Residual) | 그 자리에서 짧게 설명하거나 생략 |
| 분열문 | 핵심은 ~이다, 중요한 것은 ~이다 | 주어와 서술어를 바로 잇기 |
| 결산 표현 | 결국, 즉, 요약하면, 정리하자면 (반복) | 한 번만 쓰거나 생략 |
| 의의 과장 | 매우 중요하다, 주목할 만하다 | 구체적인 결과를 쓰기 |
| 셈 표현 | ~하는 셈이다 | 실제로 일어나는 일을 쓰기 |
| 말 걸기 감탄 | 잠깐, 자 이제 | 바로 본론 |
| 범위 상승 | 단순한 X를 넘어 Y | X만이 아니라 Y다, 또는 Y다 |
| 비유 남발 | 고속도로가 생기는 셈이다, 회의에서 의견을 듣는 것 | 실제 동작을 그대로 쓰기 |
| Q&A 형식 | Q. ~인가? A. ~다 | 본문 설명 안에 한두 문장으로 녹이기 |
| 반문 남발 | ~일까요? (대본에서 반복) | 한두 번만 |

## 허용하는 것

- 예시 속 단어나 Token을 가리킬 때 작은따옴표를 쓴다. 예: '사과', '그 사람'. 본문 문장과 예시 단어가 섞여 헷갈리는 것을 막는다.
- 비유는 꼭 필요할 때 한 줄 이내로 쓴다.
- 영어 기술 용어(Token, Embedding 등)는 원어 그대로 쓴다. 처음 나올 때 작은 글씨로 한글명과 정의를 붙인다.

## 용어 설명 형식

```html
<sub>약어(풀네임, 한글명): 한 줄 정의<br>
다음 용어: 한 줄 정의</sub>
```

- 처음 나오는 곳 바로 아래에 둔다.
- 정의는 일반인이 알아듣는 말로 한 줄. 다른 전문 용어로 설명하지 않는다.
- 같은 용어는 다시 설명하지 않는다.

## 자주 생기는 문제와 고친 예

| 고치기 전 | 고친 후 |
|---|---|
| 마지막 질문에 민수, 사과 모두 없음 | 마지막 질문에는 '민수'도 '사과'도 나오지 않는다 |
| 각 단계는 직전 단계에서 남은 한계를 해결함 | (문장 자체를 빼고 단계마다 남은 문제를 다음 단계와 이어 쓴다) |
| 원본이 지나가는 고속도로가 생기는 셈이다 | 원래 벡터에 새 정보를 더하기만 해서 원래 정보가 남는다 |
| 이 판단은 FFN을 거치며 뚜렷해진다 | 재료를 조합해 새 정보를 만드는 일은 FFN이 한다 (모호한 단어 대신 실제로 하는 일을 쓴다) |
| 문맥을 모른다. 재료는 같다. | '사과'는 어느 문장에 나오든 같은 벡터라서 과일인지 사죄인지 구분하지 못한다 |
